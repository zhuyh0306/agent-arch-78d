## 1. 复盘方法（3 条笔记）

1. **复盘不是流水账，是挑「最不满意的一项」找共性根因。**
   本周产出里最不满意的是 Day 11 的 RLS：5 条越权用例全绿，但跑的是策略模拟器，不是 Postgres。文档写了「不是真实 RLS」，可验收标题看上去仍像「多租户已通过」。

   多租户隔离方式、embedding 维度、密钥边界，这三类一旦接错，后面每张表、每条向量、每个日志都要返工。评审先看这些，不看命名和排版。

## 3. 最不满意的一项：Day 11 的 RLS

**问题**：验收看起来是「5 条攻击全部拒绝」，实际验证的是 `authorize_hop()` 的分支判断。它证明「策略逻辑写得对」，不证明「Postgres 真的按这个策略执行」。

**真实复测抓到的错**：第一次按文档建库时只写了 `AS RESTRICTIVE` 租户策略，`tenant-a` 读到 **0 行**。原因是 restrictive 策略只做 AND 收窄，必须至少有一条 permissive 策略放行；只有 restrictive 等于默认全拒。模拟器永远发现不了这个错，因为它不执行 SQL。

## 4. 共性根因

Day 7、9、10、11 反复出现同一模式：

| 表面问题 | 代理物 | 真实对象 |
|---|---|---|
| 提示词结构通过，算术 2.8% | 形状检查 | 计算结果 |
| HITL 四个点位画得很全 | 设计图 | 审批 UI、超时、真拒绝权 |
| 架构故障域表很完整 | 设计表 | 故障注入后的实际行为 |
| RLS 5 条用例全绿 | 策略模拟器 | Postgres 执行 |

**根因：把「同构代理物」当成「目标运行时的证据」。** 验收标准默认成「产物存在且自洽」，而不是「在目标组件上成立」。Day 6 已经踩过一次（资料说 pgvector 可用 → 本机 `CREATE EXTENSION` 失败），第 2 周又复发，说明这是流程问题，不是某一天的疏忽。

**流程修正**：从今天起，每条验收必须标 L1–L4；凡是「运行期成立」的结论，必须到 L3。L1 / L2 可以写进报告，但不能用「通过」两个字。

## 6. 阻塞项修复记录

### 6.1 修什么

只修「Day 11 的 RLS 断言没有运行期证据」，不改业务表、不加审批 UI。

### 6.2 怎么修

1. 只起 `postgres` 一个容器，不拉起整套栈。
2. 建临时库 `tenant_rls_demo`、临时角色 `app_rw_demo`（非 owner、`NOBYPASSRLS`）、表 `orders`。
3. 开 `ENABLE` + `FORCE ROW LEVEL SECURITY`。
4. 第一次只建 restrictive 策略 → `tenant-a` 读到 0 行，确认「restrictive 不能单独存在」。
5. 补一条 permissive 放行策略，再保留 restrictive 租户策略。
6. 复跑 5 个动作，结果如下。
7. 删除临时库与角色，未触碰 Langfuse 的 `postgres` 库。

### 6.3 复跑结果（Postgres 16）

| 动作 | 结果 | 判定 |
|---|---|---|
| `app_rw` + `app.tenant_id='tenant-a'` 读 | 1 行（只有 tenant-a） | 通过 |
| `app_rw` 插入自己的行 | `INSERT 0 1` | 通过 |
| `app_rw` 未设置租户上下文读取 | 0 行 | 通过（fail closed） |
| `app_rw` 跨租户插入 tenant-b | `new row violates row-level security policy "orders_tenant_isolation"` | 通过 |
| 超级用户读取 | 3 行（全部） | 符合预期：超级用户绕过 RLS |
