## 精读笔记（3 条，能复述才算）

1. **顺序链、条件路由、并行执行解决的是三种不同的不确定性**
   - 顺序链：A → B → C，上一步输出是下一步输入；简单可预测，但流程僵硬，无法按内容改道。适合文档处理、内容生成、数据转换。
   - 条件路由：先分类再分派到不同分支；灵活、资源利用率高，但路由分类错会把整条流程带错。适合智能客服、多功能助手。
   - 并行执行：独立子任务同时跑再汇总；速度快，但要处理并发控制与结果合并。适合多维度分析、批量处理。
   - 架构含义：这三种都是 workflow，路径由代码定；只有下一步依赖中间结果且事先不可知时才升级到 agent。今天的图把路由放在 Gateway / Runtime，把动态决策留给 Harness。
   - 落点：`docs/architecture.md` 第 1、5 节。

2. **上下文是有预算的，历史记录要按策略压缩，不是能塞多少塞多少**
   - 上下文由系统提示、工具定义、历史记录、检索内容、用户输入五层构成；按 200K 窗口的示例预算：系统 10%、工具 20%、检索 25%、历史 30%、输入 5–10%、缓冲 5%。
   - 历史压缩四法：滑动窗口（保留最近 N 轮）、阶梯摘要（每轮增量摘要）、分层摘要（近期完整、远期摘要）、关键轮标记（只留重要轮次）。分层摘要最常用：最近 3–5 轮完整，更早转结构化摘要。
   - 渐进式披露：按阶段注入工具与规则，不一次性全塞；上下文压缩链：每步只把精炼摘要传给下一步；上下文水印：在上下文中标记策略版本与 token 消耗，便于诊断。
   - 架构含义：CE 层不是「拼字符串」，要有预算、压缩与版本标记；Trace 必须记录 prompt / 契约版本，否则无法复现上下文。
   - 落点：`docs/architecture.md` 第 4、8 节。

3. **四层职责的价值在故障域，不在框图画得整齐**
   - Gateway / Runtime / Harness / 治理层，每层只能在不偷看别层内部状态的前提下完成职责：Gateway 不知道 prompt，Runtime 不知道 provider key，Harness 不知道租户策略，治理层不碰单次请求数据。
   - 两个「网关」必须分开：接入网关负责认证、租户、限流、路由；模型网关 LiteLLM 负责模型路由、provider key、成本与重试。合并后接入侧会拿到不该拿的 key。
   - 故障域要能直接回答「哪层挂了还能用」：治理层与可观测层可降级继续；Gateway、数据层、模型网关挂了必须停服；高风险动作在策略引擎不可用时 fail closed。
   - 落点：`docs/architecture.md` 第 3、6 节。
